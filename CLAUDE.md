# Lista — setlist planner for Mass

Offline-first PWA to prepare the music of a Mass: build a list from the songs, change the
key of each one for that list only, read it on a tablet or phone with no connection, print it.
Part of Músicos Católicos. TypeScript client (no framework), Slim 4 + PDO JSON API, own MySQL
database. Layout and commands: `README.md`. Deploy and hosting: `DEPLOY.md`. What is left:
`TODO.md`. Design the owner has settled: `DESIGN-LOCK.md`.

## Locked design

`DESIGN-LOCK.md` lists the parts of the interface the owner has settled: the bar and the sync dot,
the menu, the lists screen with its starred section, the inside of a list, and singing. **Do not
change them** unless the owner asks for it in that session; if a task seems to need it, ask first.
Read that file before touching any screen, and keep its standards (identical on every device, no
font-drawn marks, `rem` spacing) in everything else.

## Source of truth: musicos-catolicos

The public site (`rudypalacios/musicos-catolicos`) owns how a song is read, shown and printed.
This app must behave the same:

- ChordPro parsing (`ChordPro.php`), chord names, Latin/English notation and transposition
  (`Chord.php`, `song.js`), syllable underline (`Syllable.php`) and the print cascade
  (`PrintLayout.php`: normal, compact, two columns, several pages) are **ported to TypeScript
  as they are**. The port is checked against golden fixtures generated by running the PHP
  code, so the two cannot drift silently.
- **One difference the owner asked for (2026-11-08):** Cb, Db, Fb, Gb and Ab are shown as B, C#, E, F# and G# (Si, Do#, Mi, Fa#, Sol#), written or transposed to, Eb as D#, and E#, B#, A# as F, C, Bb, so the black keys read C# D# F# G# Bb (`PREFERRED_SPELLING` in `chord.ts`; the golden test applies it to the expected values; the public site still writes the flats). Bb, C#, D#, F#, G# stay as they are.
- **A second difference, in CSS only (the owner asked, 2026-11-23):** a stanza of only chords and notes (an intro written with `{ci: Intro}` and a line of chords) takes no verse number and its chords have no empty row of text under them, on screen (`sheet.css`) and on paper (`print/print.css`); the HTML, and so the golden fixtures, are the site's. The public site still numbers such a stanza.
- **The editor's preview is drawn another way (the owner asked, 2026-11-24):** to put a chord on a syllable by touching it, the preview cuts every line at its syllables and gives each a slot for its chord, empty where it has none (`chordpro/edit-sheet.ts`, which still draws through `sheetHtml`; `chordpro/places.ts` says where each place is in the text). Only the editor's preview: reading, singing, sharing and print draw with `sheetHtml` as they are, and the golden fixtures stay the site's.
- If something there can be better, **propose it to the owner for approval** before diverging;
  never change the behaviour on your own. When the public site changes, regenerate the fixtures
  (`npm run fixtures -- ../musicos-catolicos`) and read the diff.
- Ported so far: parser, chords and transposition, the lyrics HTML and the syllable splitter
  (`web/src/chordpro/`), and the print cascade (`web/src/print/layout.ts`). The note at the end of a line and the
  chord in parentheses (phase 7) come from the public site's PR #43.
- Chords are stored in English notation, shown in Latin by default. Minor written as `A-` or
  Latin uppercase (`SOL`, `MIm`) is normalised only by the importer, never by the parser. A chord typed
  with a lowercase letter (`[c]`, `[am]`) is capitalised by the editor when it previews and saves
  (`web/src/chordpro/capitalise.ts`), also not by the parser.
- A list carries its own sections (`Setlist.parts`; the code says "part", the person reads "sección"); the Mass is a
  template like any other (made by the app the first time, with a fixed id: `MISA_ID` in `data/templates.ts`; its sections are
  `massSections` in `mass.ts`, whose ids are inside the owner's lists: never rename them). A list copies the sections of a
  template when it is made and a template never changes a list that exists.
  Mass parts use the standard names of the Roman Missal (Ofertorio, Señor, ten piedad,
  Cordero de Dios…), not local ones.

## Rules that keep it offline-first

- What the person has offline lives in **IndexedDB** (data) and the worker's **shell cache**
  (the app). The worker never caches `/api/`. Data is never in the shell cache, so a new app
  version cannot wipe it.
- A new version installs in the background and waits; the person accepts it ("Hay una versión
  nueva"). Never `skipWaiting()` on its own.
- Records are created with client-generated UUIDs and synced from a queue, so everything
  works offline. Until synced, the device holds the only copy: say so in the UI.
- The server is the source of truth; a device that loses its storage must be able to recover. A pull goes from a cursor, so a record a device read with an older app (which dropped the fields it did not know) would never be read again: **a sync the person asks for (the dot, pulling down) is a full one** (`syncNow({ full: true })`, from cursor 0; newest edit still wins and pending edits are kept), and **whenever a record gains a field, `PULL_SHAPE` goes up** (`data/pull-shape.ts`) so each device does one full sync by itself.
- **Never a blank screen, never a silent wait.** The page carries a splash until the app draws; a
  device that holds songs opens from them without waiting for the network and checks the session in
  the background; every API request has a timeout; an error while starting shows `showFatal`. An
  update says what it is doing at each step (`web/src/updates.ts`, its states are a tested pure
  function). Anything slower than a moment shows a spinner and a sentence.

## Compatibility with the owner's data (the owner's decision, 2026-10-29)

The app is not in production, but **the owner has real information in it** (on their devices and on their
server), and some of it must keep working for certain. So:

- **Keep a shim when removing it would break the app today** with what the owner's devices and server hold
  (a stored record without a field the code now reads, an older app or a queued write that omits a value, the
  upgrade of the on-device database from an earlier version). When in doubt about safety, keep it.
- **Remove a shim when nothing the owner has needs it** (a fallback for a server or a record that cannot exist
  any more). Do not add shims for cases that cannot happen.
- The shims that are kept, and why, are listed in `TODO.md` ("Compatibility shims"). Say in `DEPLOY.md` when a
  change makes data the owner has unreadable or wrong.
- A change of shape is a **new** migration file; never edit an applied one.
- **Update (the owner, 2026-10-31):** the app has one user and nothing he cannot make again, so a change may **start a
  kind of record from scratch** (a migration that removes it, and the device dropping its copy when it opens the new version,
  as IndexedDB version 3 does with the lists) instead of converting it, and old versions of the app need not keep
  working with new data. Say so in the PR and in `DEPLOY.md`; never ask the owner to run SQL or clear a device by hand
  when a migration or the app can do it. Defaults that guard against a missing value (`null`, `undefined`) stay, with the
  default well defined.

## Database

Migrations are numbered `.sql` files in `migrations/`, applied by the app itself on the first
request after a deploy (the host has no shell and the CI only deploys). Never edit one that
has been deployed; add a new file. Write for MySQL **and** SQLite (tests use SQLite): the
common subset, one `;` per statement, idempotent (`IF NOT EXISTS`). What the subset cannot say
(table charsets) goes in a file named `NNNN_name.mysql.sql` or `.sqlite.sql`, which only that
database applies. Every new MySQL table needs a `.mysql.sql` follow-up that makes it `utf8mb4`:
the host's database may default to 3-byte `utf8`. Run the suite against a
MySQL-compatible server (`TEST_MYSQL_DSN`, see `tests/Support/TestDatabase.php`; MariaDB is what the
sandbox can install, production is MySQL) whenever a migration or a query changes.

## PDF import

`web/src/pdf/layout.ts` (pure, tested) turns the text items of a PDF page into the text the importer
reads, putting every chord over the syllable it is over by its x position; `read.ts` is the pdf.js
glue, loaded lazily. pdf.js must work inside the page's CSP: no eval, no WebAssembly (`useWasm:
false`), its worker is a file of this origin (built first, its URL injected as `__PDF_WORKER_URL__`).
`tests/e2e/pdf.ts` makes a real PDF with Chromium, imports it under the production policy
(`enforcePolicy` in `tests/e2e/lib.ts`, which reads it from `public/.htaccess`) and checks every
chord. The built app splits code (esbuild `splitting`): everything `main` imports statically must be
precached (the build follows the imports), what loads on demand must not be.

## Image import (a photo of a sheet)

Importar also reads a photo or a screenshot (`web/src/ocr/`), on the device like the PDF: nothing is sent anywhere, so the
privacy text stays true. Tesseract (WebAssembly, a worker of this origin) reads the picture twice (`read.ts`): once for
everything and once with an alphabet of only what a chord is made of (the first reads a lone `C` as `e`); `words.ts` (pure,
tested) puts the two together, takes the tilt out, tells the columns apart and hands the words to the PDF's `pdf/layout.ts`,
so a chord lands on its syllable the same way. It is for printed chords; handwritten ones are tried, with no promise, and the
review says so. `scripts/build.ts` copies the reader's files to `/assets/ocr/` (served as they are, not precached), and the
policy in `public/.htaccess` allows `wasm-unsafe-eval` for it (the only widening: no other domain, no `eval` of text).
`tests/e2e/photo.ts` makes a picture with Chromium (straight and crooked), imports it under the production policy and checks
every chord. Real photos and screenshots are not in the repo (they are other people's songs); the tests use invented lyrics.

## Trying the app with no account (the owner's decision, 2026-11-02/03)

The app is not behind a login. A device with nothing on it and no session opens on the welcome ("Continuar con Google" / "Usar mi correo" / "Probar sin cuenta",
`web/src/views/welcome.ts`); trying it makes the device a **guest** (`web/src/guest.ts`: the store's owner is `GUEST_OWNER`, which is not an email,
so no account can have it). A guest writes songs, lists and templates to the device like anyone, they wait in the queue, and **nothing is synced**
(`App.syncNow` and `requestSync` do nothing while `guest`; the status is `local`). Signing in asks, once, only if something was written, what to do with it:
`App.adoptKeepingGuestWork` (it joins the account: the records carry client UUIDs, so signing in only changes whose they are and syncs; the Mass is stamped
as the oldest so the account's own always wins) or `App.adopt` (drops it). Cancelling the question changes nothing and ends the session the sign-in made.
The bar, the dot and Ajustes say there is no account (`DESIGN-LOCK.md`). Sign-up with email, and Google, are below.

## Accounts of other people (step 3 of "Open sign-up": 3a the server, 3b the app)

`POST /api/register` makes an account and opens its session; the address is confirmed by a link sent to it (`Auth/Accounts.php`, `Auth/EmailTokens.php`),
and a forgotten password is chosen again by another (`/api/forgot`, `/api/reset`). Rules that matter: **sign-up is open to anyone** (the owner decided on 2026-11-04 not to keep a switch); the app stores other people's emails, and what it says about
that is its own page, `/privacidad` (`web/src/views/privacy.ts`), linked from the sign-up form and Ajustes: **when what is stored, for how long or who gets it changes, that text changes in the same PR**
(its numbers are the server's). The public site's policy is not changed until the owner mixes the two systems; the **links in the emails point at `APP_URL`**
(default the production address), never at the host of the request (a reset link that followed `Host` would hand the code to whoever asked);
a link's code is 256 random bits, only its hash is kept, it works once and expires; `/api/forgot` answers the same whether or not the address has an
account; a new password ends every session; sign-up and forgot need a **proof of work** solved by the browser (`Security/ProofOfWork.php`: SHA-256 with
18 zero bits, signed by the server with a secret it makes itself in `app_secrets`, spent once) because the policy forbids a third-party captcha. It prices a
script, it does not tell a person from a program: the limits per address (`Security/RateLimiter.php`) and the confirmation of the address do the rest.
Email goes through the site's mailbox over SMTP (`Mail/SmtpMailer.php`, PHPMailer); its settings are the `MAIL_*` of the owner's other system (`MailConfig`); with no `MAIL_HOST` it is written to the error log (`LogMailer`).
Every account is separate: records are keyed by (user, id) (migration 0016). The accounts that existed before confirmation (the owner's) count as confirmed.

**The app (3b):** the welcome (`views/welcome.ts`, the owner chose it on 2026-11-27 from a mockup) offers three ways in: Google, "Usar mi correo" and, quiet as a text link, "Probar sin cuenta", under the mark of Músicos Católicos, its name and what the app is for, **all centred, in that order** (the owner, 2026-11-27; `views/brand.ts`: the ring with a cross as the public site draws it, and the name in Bricolage Grotesque, which the app already carries for printing). The icons in `public/` are made from the same drawing (`web/brand/icon.svg`). "Usar mi correo", the guest's line ("Crear cuenta") and Ajustes
("Ya tengo cuenta") all open **one access screen** (`views/access.ts`): the tabs **Entrar | Crear cuenta** (a session that ended shows only Entrar), Google on top, then the form of the tab (`views/signin.ts`, `views/signup.ts`; changing tab keeps the email typed).
The sign-up form checks what it can itself (`account.ts`), asks for a puzzle and solves it on the device (`pow.ts`: SHA-256
written out, with the first blocks mixed once, in slices so the screen moves; no worker and nothing from another domain), then registers; the person lands on
`/ajustes/correo` ("Te mandamos un enlace") already signed in. **The only thing said about privacy on these screens is one link, "Lee la privacidad"** (the owner, 2026-11-27: no "te mostramos cómo usamos tus datos" and no checkbox; the server never kept the checkbox, and
`/privacidad` says in its first line that the data is used for nothing else): keep it that short, and keep that page short (`views/privacy.ts`; `web/test/privacy.test.ts` limits its length). A guest who signs up is asked **bring it to my account / start from zero / cancel**
(`shell/session.ts`, `adoptGuestWork`, the same choice as when signing in, with other words); cancelling ends the session just made and keeps them as a guest.
**The screens before anybody is in** (welcome, access, forgot, `/privacidad`, the links of the emails) have no menu rail: `#app.is-gate` stacks the bar over the screen (from 900px the app is a row, for its rail), and `.page--gate` is one column of 26rem, no box. `tests/e2e/gate.ts` checks it.
The links of the emails open pages of their own that need no session and no data of the device (`/verificar/:token`, `/restablecer/:token`, `views/account-link.ts`, drawn
by `main.ts` like the visitor's page). `tests/e2e/signup.ts` covers it end to end with a little SMTP server that receives the server's real emails.

## Deleting an account, and signing out (the owner's decision, 2026-11-28)

A person can delete their own account (Ajustes, at the end → `/ajustes/eliminar`, `views/delete-account.ts`), in three steps made so nobody does it by chance: (1) the app asks the server to send a **link to the account's email** (`POST /api/account/delete-request`,
`Auth/AccountDeletion::request`, code purpose `delete`, 1 hour); nothing changes. (2) The page of the link (`/eliminar/:token`, `account-link.ts`) **shows what goes and asks**: opening a link never deletes (a program that reads the links of an email would), and "Sí, eliminar mi cuenta"
(`delete-confirm`) **locks the account for 3 days** (`users.delete_after`, migration 0023): every session ends, its shared links stop (the two share queries join `users` with `delete_after IS NULL`) and `RequireUser` answers **403 `deletion_pending`** to everything but `GET /api/me` and `POST /api/account/keep`
(`allowPending`). (3) After the 3 days it is **deleted for good** with everything it owns (`AccountDeletion::OWNED`: **a new table with a `user_id` goes in that list, and in its test**); `PurgeDueAccounts` runs it on any API request, because the host has no cron. Signing in again in the 3 days (password,
Google, the sign-in of a device whose session ended) shows **`keepAccountView` over everything** (`showKeepAccount`, `session.ts` `guardPending` / `finishGoogle`): "Conservar mi cuenta" (`/api/account/keep`) or "Seguir con la eliminación" (ends the session). A device whose account is locked reads the 403 as a session that ended
(`errorKinds.isSignedOut`). The privacy text says all of it (`views/privacy.ts`, "Tus derechos"): **when this changes, it changes there in the same PR.** If the owner deletes their own account and it is the only one, `seedOwner` makes it again, empty, from `OWNER_EMAIL`.

**"Descargar mis cantos"** (the account card, and the delete screen, for guests too): a `.zip` made **on the device** (`export.ts` pure + tested, `zip.ts` a store-only zip with UTF-8 names, `download.ts` the glue), so it works offline: `cantos/<title>.txt` per song, as ChordPro with `{title}` and `{artist}`, and `listados.txt` with every list in the order of the Mass, each song in its key. iPad: a download from the installed app is checked by hand.

**"Cerrar sesión"** (it was "Salir") asks "¿Cerrar sesión?" first (`shell/frame.ts`): signing out takes the songs off the device, and without a connection they cannot be opened until the person signs in again. The unsent-songs question still comes after it when it applies. Ajustes has the account as a **card at the top**
(`views/account-card.ts`), the rail's foot is the person's letter (ring = the sync dot's colour) and address and leads to Ajustes; the mockup the owner chose and the locked design are in `DESIGN-LOCK.md` ("Menu"). Classes of this area are named `acct__*` / `delete-account__*` on purpose: `.chip` and the like already exist elsewhere (`.chip` of the editor was overwritten once).

## Signing in with Google (step 4 of "Open sign-up")

A redirect flow done by the server: no script of Google is loaded in the page, so the CSP is unchanged (a link the browser follows is not governed by it). "Continuar con Google" is a plain link to `GET /api/google/start`
(`Http/Actions/GoogleStartAction.php`), which sends the browser to Google; Google sends it back to `GET /api/google/callback` (`GoogleCallbackAction.php`), which opens the session and redirects to `/?google=<word>`; the app reads the word once
and removes it from the address (`web/src/google-return.ts`, `shell/session.ts`). The button appears only when `GET /api/auth-options` says the server has `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` (`GoogleConfig`; with neither,
the app is as before). Rules that matter:

- Only `openid email` is asked (no name, no photo) and `prompt=select_account` (a tablet in a parish is shared). **Do not widen the scopes without telling the owner and changing `/privacidad` in the same PR.**
- **Login CSRF:** the `state` is not enough, so the sign-in is tied to the browser that started it by a cookie (`lista_oauth`, `Http/OAuthCookie.php`, path `/api/google`, 10 minutes) whose hash is stored with the state
  (`Auth/Google/OAuthStates.php`, table `oauth_states`: only hashes, one use, 10 minutes, PKCE verifier and nonce kept server-side). A return without that cookie signs nobody in.
- The ID token comes straight from Google's token endpoint over TLS, so its signature is not checked (OpenID Connect Core 3.1.3.7); `GoogleIdentity::fromClaims` checks issuer, audience, expiry, nonce, `sub` and **`email_verified === true`**.
  An address Google has not confirmed signs nobody in (`unverified`).
- **Which account (`Auth/Google/GoogleAccounts.php`):** the person is found by Google's `sub` (table `identities`), never by email once linked; else by the **confirmed** address of an existing account (it is joined and keeps its password);
  else an account whose address **nobody confirmed** is claimed (its password and sessions and links are dropped: otherwise whoever registered a stranger's address would get the stranger's data); else a new account is made, already
  confirmed, with a password hash of random bytes nobody knows (`users.password_hash` is `NOT NULL`; the person can choose one with "Olvidé mi contraseña"). Never merge by an address Google has not confirmed.
- Every return ends on `APP_URL` (never the request's `Host`), with one word: `ok`, `new` (an account was made, so a guest is asked as in a sign-up), `cancelled`, `unverified`, `busy`, `unavailable`, `failed`. Anything unknown is `failed`.
  The code, the state and Google's answers are never logged. Starts and returns are limited per address (`RateLimiter`, kinds `google-start` and `google-return`).
- `GOOGLE_AUTH_URL` and `GOOGLE_TOKEN_URL` exist only so `tests/e2e/google.ts` can put a stand-in for Google (`tests/e2e/fake-google.ts`, which checks client, secret, redirect and PKCE) in its place; they are never set on the server.
- The privacy text says what is kept (the email and Google's id) and that Google learns of the sign-in; **when this changes, `views/privacy.ts` changes in the same PR.** Safari on the iPad (the installed app going to Google and coming back) is
  checked by the owner by hand (`DEPLOY.md`, "Entrar con Google").

## Sharing a list

A list can be shared by a link anyone can open, read only (the owner's decision, 2026-11-01: "cualquiera"). It is the one thing of this
app that is public, so it says as little as it can: `GET /api/shared/:code` answers only the title, the sections the list shows, the songs in
order with the key each has in it, which songs share a page (`withNext`: the owner divided it while singing, and the visitor reads the same pages) and, if the person chose it, the lyrics (`src/Share/ShareRepository.php`); never the account, the notes, the
tags or anything else (but the link to hear the original of a song that has one: see "A link to hear the original"), and a stopped, never given or malformed link all answer the same 404. The visitor's page (`/c/:code`, `web/src/views/shared.ts`)
is drawn like the public site's pages and loads nothing from another domain, sets no cookie and has no analytics or ads: the privacy text
proposed for the public site says so, so **do not add any of those without telling the owner first**. The words belong to their authors: the
sheet asks whether the lyrics go with the link, the page says "uso personal" and links to the public site's copyright page. Stopping a share
kills its link for good (a new share is a new code). **One song** can be shared the same way (`src/Share/SongShareRepository.php`, table `song_shares`; the owner's decision, 2026-11-02): the answer has the
shape of a list of one section and one song (`kind: 'song'`), in the song's own key, and its lyrics always go (a song without them shows nothing), so its sheet has no lyrics switch. **The preview:** a chat app reads only the HTML
the server sends, so `public/index.php` writes the name of the list or song into the `<title>` and `og:` tags of `/c/:code` (`SharePreview`, `Http/ShellPage`). It says only what the page itself says to anyone with the
link, a link that shows nothing gets the plain shell, and its misses count against the same throttle. `tests/e2e/share.ts` covers it end to end under the production policy.

The visitor's page is the same PWA: it registers the app's service worker and keeps a copy of the list it opened in a database of its own
(`web/src/shared-store.ts`, `lista-shared`, never mixed with the owner's data), so it opens with no connection and says it is a copy and from when; a
link found stopped (404) deletes its copy. That copy and the visitor's reading preferences (key, size, notation, chords shown or hidden) are the only things stored on a
visitor's device, and the privacy text proposed for the public site says so. The page is built to read the words: a one-row header, the foot of the
site folded away (a small tab at the bottom edge), and a song shown as when singing (the app's `createReader`, lyrics fitted to the screen, the tools
folded under the bar, a swipe or ← → to change song). Keep it that way: the lyrics get the screen.

## A link to hear the original (the owner's decision, 2026-11-24)

A song carries one optional link (`Song.listenUrl`, column `listen_url`, synced with the record; it goes in a shared list or song **whenever the song has one, with no switch** (the owner, 2026-11-25: `listenUrl` in `GET /api/shared/:code`, the ♪ in the visitor's list and an option in the visitor's tools, the player in a sheet, nothing of YouTube before the touch)). It is a reference, not a
music player and not hosting: nothing is stored but the address. `web/src/listen-url.ts` (pure, tested) says what a pasted text is: a YouTube or
YouTube Music video (a player in the page), any other `https` link (a button that opens apart) or nothing usable. The way in is an option "Escuchar el original" of the "⋯" sheet of a song
(`views/listen.ts`: its page, a row of a list, singing) and a ♪ in the rows of a list that have a link and in the tools row of the song's page, before its "⋯" (the owner: the same icon everywhere, **drawn only where there is room, from 600px: a tablet or a window; on a phone it is not drawn and the option of the "⋯" sheet is the way in, and from 600px that option is not repeated there** (`.listen-in-menu`, 2026-11-26); and in the singing bar beside the key, under the same rule); there is no row on the page (it cost the lyrics screen). On the page of a song
it creates YouTube's own player (`youtube-nocookie.com`, a sandboxed frame) as a window dragged by its bar, **everywhere it appears (the owner, 2026-11-26: no docked player any more)** (`views/float.ts`: `position: fixed`, nothing behind it, so the lyrics stay touchable and scrollable; on a phone it may be pushed past an edge leaving its bar in sight; its place is remembered on the device). The owner chose to be able to push it out of sight (2026-11-25) knowing YouTube's terms ask for the player to be in sight. Closing it (✕)
removes the frame, which ends the sound. **Rules that matter:** the frame's address is always built from the video id, never from the
pasted text; **nothing of YouTube loads before that touch** (the one widening of the CSP is `frame-src https://www.youtube-nocookie.com`, and `Referrer-Policy`
is `strict-origin-when-cross-origin` because the player refuses to play with no referrer); the player is not hidden or shrunk under 200 px to leave only the
sound (YouTube's terms); the privacy text says it (`views/privacy.ts`, "terceros"). Later the references are meant to be the owner's own (musicoscatolicos.com
and the tutorials): another kind of link is a new case of `readListenUrl`, and each new domain is a deliberate widening of the CSP with the privacy text in
the same PR. `tests/e2e/listen.ts` covers it under the production policy.

## Public repository

Nothing private goes in the repo: no `.env`, no real server paths, user names or database
names in docs (use placeholders), no default credentials. Secrets live in the `production`
environment on GitHub and in `.env` on the server.

## Policies

The app is private (login, `noindex`, no ads, no analytics, nothing loaded from another
domain: the CSP in `public/.htaccess` enforces it), except the pages of a list its owner shared ("Sharing a list") and **the YouTube player** ("A link to hear the original"). **Before** a change that opens it to other
people, loads anything from another domain, adds analytics or ads, stores new kinds of
personal data or publishes songs of others, tell the owner and propose the privacy text: the
public site's policies (`musicos-catolicos`, `src/Templates/legal/`) must keep describing what
the code really does.

## Working with the owner

- **One branch per PR, cut from `main`.** Before pushing, check the branch's PR is not merged (never push to a merged or closed
  PR; open a new one). If the environment fixes a branch name, use it only when its previous PR is merged, and restart it on
  `main` (`git fetch origin main && git checkout -B <branch> origin/main`) without bringing its old history; if that is not
  possible, tell the owner before going on. Never merge an old branch back in: with squash merges it fills the PR with commits
  that are not that change. This replaces the older advice to merge `main` into the work branch.
- **One PR groups several changes (the owner's rule, 2026-11-21).** Do not open a PR per change: while a branch's PR is open, every
  new change of the session goes into the same branch and the same PR, and the PR text is updated. A new PR is opened only when the
  one before has been merged (next rule), or when the change is a different thing the owner would release on its own.
- **A merged branch gets no more commits (the owner's rule, 2026-11-21).** Once a branch's PR is merged, commit nothing more on it
  and push nothing more to it: every follow-up, however small (a fix, a change the owner asked for in the same conversation),
  goes on a **new branch cut from the current `main`** with a **new PR**. Check whether the PR is merged **before every push**, not
  only before the first: the owner may merge while the work goes on, and what is pushed after the merge never reaches `main`.
  If the environment fixes the branch name, it is reused only by restarting it on `main` as above; otherwise take a new name.
- The owner works only from claude.ai: they cannot run scripts, so everything must be doable by the
  app, the deploy or a SQL query in phpMyAdmin. Ask for one thing at a time, with the exact steps.
- **Open the PR yourself whenever the change makes sense and could be released** (checks green, one coherent change): the owner
  does not have to ask for it (the owner's decision, 2026-11-15). This overrides a default of waiting to be asked. Before opening
  one, list the open PRs of the branch: something may already have opened it. Do not open one for work that is half done, only
  an experiment, or that the owner has not decided yet.
- Claude runs every check; GitHub only deploys. Claude opens PRs and **never merges**: the owner merges
  (squash). After a squash merge, new work starts on a fresh branch from `main` (see the first rule of this section).
- Production: cPanel shared host, PHP 8.3, MySQL (the database was created as plain `utf8`, migration
  `0003` fixes the tables), FTPS deploy by the `production` environment; the site is
  `lista.musicos-catolicos.com`. The public site and the admin (`musicos-catolicos`,
  `mc.musicos-catolicos`) are separate repos; the public site's parser and printer are the reference.
- Fixtures and tests use invented lyrics. The owner's real PDF is not in the repo and is not needed.

## A fresh sandbox (nothing survives between sessions)

```
composer install && npm install
# MySQL-compatible server for the SQL checks (MariaDB is what apt offers):
apt-get update && apt-get install -y --no-install-recommends mariadb-server
mkdir -p /run/mysqld && chown mysql:mysql /run/mysqld
mysql_install_db --user=mysql --datadir=/var/lib/mysql; (mysqld_safe --user=mysql &) ; sleep 8
mysql -e "CREATE DATABASE lista_test CHARACTER SET utf8mb4; CREATE DATABASE lista_utf8 CHARACTER SET utf8;
  CREATE USER 'lista'@'127.0.0.1' IDENTIFIED BY 'lista';
  GRANT ALL ON lista_test.* TO 'lista'@'127.0.0.1'; GRANT ALL ON lista_utf8.* TO 'lista'@'127.0.0.1';"
# then: TEST_MYSQL_DSN='mysql:host=127.0.0.1;dbname=lista_utf8;charset=utf8mb4' vendor/bin/phpunit
```

Chromium and Playwright are preinstalled (the e2e scripts load Playwright with `createRequire`). The
fixtures need the public site next to this repo (`add_repo` `rudypalacios/musicos-catolicos`, clone it as
`../musicos-catolicos`). Do not `pkill -f` a pattern that appears in your own command line, and do not
chain a force-push into a longer command: both end the shell.
